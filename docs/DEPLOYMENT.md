# Deploying Rahasya

How Rahasya runs in staging and production, how to set it up the first time, how to release, how to look at the production database safely, and how backups and rollbacks work. Local development is in the root [`README.md`](../README.md).

## How it fits together

```text
        Android app (APK)                Browser
               │                            │
               │            ┌───────────────┤
               │            │ Vercel        │ Vercel (later)
               │            │ web app       │ admin console
               ▼            ▼               ▼
        ┌─────────────────────────────────────────┐
        │ Render: API (NestJS)                     │  receives only ciphertext, a hash of the
        │ runs database migrations on every start  │  auth key, and account metadata
        └────────────────────┬────────────────────┘
                             ▼
        ┌─────────────────────────────────────────┐
        │ Neon: PostgreSQL 16                      │  branches: main (production), staging
        └─────────────────────────────────────────┘
```

| | Staging | Production |
| --- | --- | --- |
| Git branch | `main` | `release` |
| API | `rahasya-api-staging` on Render | `rahasya-api` on Render |
| Database | Neon branch `staging` | Neon branch `main` |
| Web app | Vercel preview for `main` | Vercel production (domain of your choice) |
| Android | EAS profile `preview` | EAS profile `production`, attached to a GitHub Release |
| Deploys when | a commit lands on `main` | `main` is pushed to `release` |

Everything above runs on free plans. Two limits to know: Render's free API sleeps after a while without traffic, so the first request afterwards can take up to a minute; and Vercel's Hobby plan is for non-commercial use.

The config lives in the repository: [`render.yaml`](../render.yaml) (API), [`apps/app/vercel.json`](../apps/app/vercel.json) (web app), [`apps/app/eas.json`](../apps/app/eas.json) (Android builds), [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) (tests on every push and pull request) and [`.github/workflows/backup.yml`](../.github/workflows/backup.yml) (nightly backup).

## First-time setup

Do these once, in order. Each step needs the URLs from the one before.

### 1. GitHub

1. Push the repository to GitHub and create the `release` branch from `main`: `git push origin main:release`.
2. Protect `main` and `release` in **Settings → Branches**: require the **CI** check to pass before merging.

### 2. Neon (database)

1. Create a project, PostgreSQL 16, in the region closest to your users (for India, Singapore).
2. The default branch is `main`: that is **production**. Create a second branch named `staging` from it.
3. For each branch, copy the **direct** (not pooled) connection string. The API's migrations need a direct connection.
4. Create a read-only role for looking at production and for backups. In the SQL editor on the `main` branch:

   ```sql
   CREATE ROLE rahasya_readonly WITH LOGIN PASSWORD '<a long random password>';
   GRANT CONNECT ON DATABASE neondb TO rahasya_readonly;
   GRANT USAGE ON SCHEMA public TO rahasya_readonly;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO rahasya_readonly;
   GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO rahasya_readonly;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO rahasya_readonly;
   ```

   Its connection string is the production one with `rahasya_readonly` and its password in place of the owner's.

### 3. Render (API)

1. **New → Blueprint**, pick the repository. Render reads `render.yaml` and creates `rahasya-api-staging` and `rahasya-api`.
2. It asks for the values marked `sync: false`. Fill them per service:

   | Variable | Staging | Production |
   | --- | --- | --- |
   | `DATABASE_URL` | Neon `staging` direct connection string | Neon `main` direct connection string |
   | `CORS_ORIGINS` | Vercel's address for `main` (step 4), e.g. `https://rahasya-git-main-<you>.vercel.app` | your web app's domain, e.g. `https://app.rahasya.app` |
   | `ADMIN_RP_ID` | admin console host (once it exists) | admin console host |
   | `ADMIN_ORIGIN` | admin console URL | admin console URL |
   | `ADMIN_IP_ALLOWLIST` | your IP addresses or ranges | your office or VPN ranges. **Never `*` in production**; unset blocks everyone |
   | `RECOVERY_PUBLIC_KEY` | leave empty until emergency recovery is set up | the organisation's offline public key |

   `JWT_SECRET` and `DATA_KEY` are generated by Render, different for each service.
3. **Copy `DATA_KEY` of production somewhere safe and offline.** It encrypts users' two-step sign-in secrets; if it's lost, everyone's two-step sign-in has to be reset.
4. Each service builds, runs the migrations, and starts. Check it: `curl -s -X POST https://rahasya-api-staging.onrender.com/auth/prelogin -H 'content-type: application/json' -d '{"email":"check@example.com"}'` returns a salt.

### 4. Vercel (web app)

1. **Add New → Project**, import the repository, set **Root Directory** to `apps/app`. Framework preset: **Other**. Install and build commands come from `vercel.json`.
2. **Settings → Git → Production Branch**: `release`. Every other branch, including `main`, gets a preview deployment; `main`'s stays at the same address (`<project>-git-main-<you>.vercel.app`).
3. **Settings → Environment Variables**:

   | Variable | Production | Preview |
   | --- | --- | --- |
   | `EXPO_PUBLIC_API_URL` | `https://rahasya-api.onrender.com` | `https://rahasya-api-staging.onrender.com` |

4. Add your domain under **Settings → Domains**, then put it in the production API's `CORS_ORIGINS`.

The site is served with security headers. Its Content Security Policy starts in **report-only** mode: the browser logs violations but blocks nothing. After the first staging deploy, open the app, sign up, unlock, add and copy an entry with the browser console open. If no CSP violations appear, rename the header in `vercel.json` from `Content-Security-Policy-Report-Only` to `Content-Security-Policy` and change `connect-src` from `https://*.onrender.com` to the exact API addresses.

### 5. Android (EAS)

1. `cd apps/app && npx eas-cli@latest login && npx eas-cli@latest init` links the app to an Expo account.
2. Builds use the profiles in `eas.json`: `development` (for local work, talks to `10.0.2.2:3000`, the host machine from the Android emulator), `preview` (staging API), `production` (production API). All produce an installable APK.

### 6. Backups

1. Make a key pair on your own computer: `age-keygen -o rahasya-backup-key.txt`. The file holds the private key: **keep it offline** (printed, or on an encrypted USB drive), never in GitHub or Render. It prints the public key (`age1…`).
2. In GitHub **Settings → Secrets and variables → Actions**, add:
   - `BACKUP_DATABASE_URL`: the production read-only connection string from step 2.
   - `BACKUP_AGE_RECIPIENT`: the public key (`age1…`).
3. Run **Actions → Nightly database backup → Run workflow** once to check it. Each night it saves an encrypted dump as a workflow artifact, kept 30 days. Neon also keeps its own short point-in-time history.

### 7. The first super admin

Render's free plan has no shell, so create the super admin from your own computer with production's settings in the environment (never committed):

```bash
cd apps/api && pnpm build
DATABASE_URL='<production direct connection string>' JWT_SECRET='<production JWT_SECRET>' \
ADMIN_ORIGIN='https://<admin console URL>' ADMIN_RP_ID='<admin console host>' \
  pnpm admin setup-super-admin you@your-domain "Your Name"
```

It prints an invite link; open it to set a password and register your security key. The same pattern runs the break-glass commands.

The CLI also reads `apps/api/.env`, and anything not given on the command line falls back to it. So pass every variable above: a missing `DATABASE_URL` would quietly run against your local database instead of production.

## Releasing

1. Merge pull requests into `main`. CI must pass (build, type checks, every test against a fresh Postgres).
2. `main` deploys to staging by itself: the API on Render, the web app on Vercel's `main` preview.
3. Check staging:
   - `API=https://rahasya-api-staging.onrender.com pnpm --filter @rahasya/api smoke` (20 checks; it creates a throwaway account each run, so only ever on staging).
   - Open the staging web app: sign in with your test account, add and copy an entry.
4. Promote: `git push origin main:release`. Render runs the production migrations and starts the new API; Vercel publishes the web app.
5. Android: tag the release and build it.

   ```bash
   git tag v0.2.0 && git push origin v0.2.0
   cd apps/app && npx eas-cli@latest build --platform android --profile production
   gh release create v0.2.0 <downloaded .apk> --title "Rahasya 0.2.0" --notes "What changed"
   ```

6. Check production the read-only way below, with your production test account.

## Rolling back

- **API:** Render → the service → **Events** → choose the previous deploy → **Rollback**. Migrations are always backward compatible for one release, so the previous API version runs on the newer schema.
- **Web app:** Vercel → **Deployments** → the previous production deployment → **Instant Rollback**.
- **Android:** point users to the previous GitHub Release.
- **Database:** never undo a migration by hand. If data itself is damaged, restore (below) into a new Neon branch, check it, then switch `DATABASE_URL`.

## Looking at the production database

Use the read-only role, so nothing can be changed by accident:

- **In the browser:** Neon console → SQL editor, connected as `rahasya_readonly`.
- **From your computer:** `psql '<production read-only connection string>'`.

Useful queries, for a test account:

```sql
select id, email, status, totp_enabled, revision, last_login_at, created_at from users where email = 'test-account@your-domain';
select name, platform, last_seen_at, revoked_at from devices where user_id = '<id>';
select count(*) filter (where deleted_at is null and blob is not null) as entries,
       count(*) filter (where deleted_at is not null and blob is not null) as in_trash
  from vault_items where user_id = '<id>';
select at, actor_label, action, result from audit_log where target_id = '<id>' order by id desc limit 20;
```

What you will and won't see: emails, statuses, device names, timestamps and the audit log are readable; every entry, group name and label is ciphertext, and keys are stored only wrapped or hashed. That's by design: even full database access reveals no vault contents. Don't point Prisma Studio at production; it can edit rows.

## Restoring a backup

1. Download the artifact from **Actions → Nightly database backup → (a run) → Artifacts**, and unzip it.
2. Decrypt and restore into a **new** Neon branch, never straight over production:

   ```bash
   age -d -i rahasya-backup-key.txt rahasya-2026-10-06.dump.age > rahasya.dump
   pg_restore --no-owner --dbname='<new branch direct connection string>' rahasya.dump
   rm rahasya.dump
   ```

3. Check it with the queries above, then point the API's `DATABASE_URL` at it if it should replace production.

Test a restore once a month; a backup that has never been restored isn't known to work.

## Secrets: where they live and how to change them

| Secret | Lives in | Changing it |
| --- | --- | --- |
| `JWT_SECRET` | Render (per service) | Change it in Render and redeploy: every session ends and people sign in again (their data is unaffected) |
| `DATA_KEY` | Render (per service), offline copy | Can't simply change: existing two-step secrets would become unreadable. Treat as permanent; if exposed, reset every user's two-step sign-in |
| Database passwords | Neon, Render, GitHub (read-only one) | Reset in Neon, then update `DATABASE_URL` / `BACKUP_DATABASE_URL` |
| Backup private key | Offline only | Make a new pair, update `BACKUP_AGE_RECIPIENT`; keep the old private key for older backups |
| Organisation recovery key | Offline only | Covered by the emergency-recovery procedure |

Nothing secret is ever committed; `.env` files are git-ignored, and the CI file contains only test values.
